# SDK Compatibility Matrix

Aouda ships multiple artifacts from separate repositories. They do **not** share a single version number. Use this matrix to pick compatible combinations.

---

## Versioning model

| Artifact | Package / image | Repo | Version scheme |
|----------|-----------------|------|----------------|
| Aouda server | `ghcr.io/aoudadb/aouda-server` (Docker), `Aouda.Server` (binary) | `aouda` | Release train (not npm SemVer) |
| TypeScript client | `@aouda/client` (npm) | `aouda-client-ts` | SemVer |
| .NET client | `Aouda.Client` (NuGet) | `aouda` | SemVer |
| Studio | `ghcr.io/aoudadb/aouda-studio` (Docker, private; **BL-1982, next train** — `aouda/studio` was never published), hosted app | `aouda-studio` | App version |

**Release order** when APIs change: server → SDKs → Studio → docs.

**Platforms** (**BL-1982, next train**). The supported platform is **Linux** — the server image is `linux/amd64` + `linux/arm64`, the archives `linux-x64` and `linux-arm64` — and the Windows archives are built but **not supported for production** ([Deployment](../deployment/index.md#supported-platform-bl-1982-next-train)). The SDKs run wherever their runtime does: `@aouda/client` on Node and browsers, `Aouda.Client` on .NET 10; the statement is about where a server runs.

**.NET target.** The server and the .NET packages (`Aouda.Client`, `Aouda.Abstractions`, `Aouda.Embedded`,
`Aouda.Testing`) target **`net10.0`** (**BL-739, 0.2.0**); every earlier release targets `net8.0`. A NuGet
package built for `net10.0` does not restore into a `net8.0` project, so an application on .NET 8 stays on the last
`net8.0` release of those packages until it retargets. The TypeScript client is unaffected.

---

## The protocol version: one rule (**BL-1830, next train**)

A server speaks **one** protocol version, and so does every SDK release: `3` from the next train. It travels in the
`X-Aouda-Protocol-Version` header of every HTTP and long-poll request and in the realtime `auth` message's `protocol_version`, and the
server answers with its own in every response's header and in `auth_ok.protocol.version` ([HTTP API: Protocol
Version](../reference/http-api.md#protocol-version)).

**An SDK and a server of different protocol versions do not talk.** The request is refused — `400 PROTOCOL_VERSION_UNSUPPORTED` on
HTTP, `auth_error` of that code on the socket — and both SDKs end for good on it (`AoudaProtocolVersionException` in C#,
`AoudaProtocolVersionError` in TypeScript): no retry, no reconnect, no fallback to long poll. An SDK also refuses a server whose
`auth_ok` names another version, or none. **There is no window**: use the SDK release published with the server, and move the server,
the SDKs and Studio's `@aouda/client` pin together. A request that names no version — `curl`, a probe, the CLI, Hub — is served.

| Release | Protocol version | What a client of another release gets |
|---|---|---|
| Server **next train**, `Aouda.Client` **next train**, `@aouda/client` **next major** | `3` | — |
| Server `0.17.1` and before | `2` (the header accepted `1`–`2`, and nothing moved it on a wire change) | A new SDK (sends `3`) is refused on every HTTP call `400 UNSUPPORTED_VERSION` ("Supported versions: 1-2"); its socket is ended by the SDK (the old `auth_ok` says `1`) |
| `Aouda.Client` `0.17.1` and before | sends `2` | Against a server of the next train: `400 PROTOCOL_VERSION_UNSUPPORTED` on every data call; a socket opens if nothing else is called (its `auth` names none) |
| `@aouda/client` `0.17.0` and before, Studio `0.16.0` and before | send `1` | The same |

The protocol version moves by one for every release whose wire contract changed since the last, additive or not; every change
between two releases shares that one bump. The server's own build holds it to that (**BL-1172, next train**): a generated
description of every route, body and realtime message is compared with the one the last release recorded, and a change while the
version is still the released one fails the server's tests — so a wire change cannot ship under an old number. Error codes are not part of
that description: a new refusal code is not a protocol change.

### Reading the matrix

- **Wire protocol** — the `X-Aouda-Protocol-Version` header's number. From the next train a server and a client of different numbers do not talk ([the one rule](#the-protocol-version-one-rule-bl-1830-next-train)); up to 0.17.1 the server accepted `1`–`2` and the number did not move on a wire change.
- **`@aouda/client`** — Minimum npm version for a server generation. Studio may pin a specific patch (see `aouda-studio/package.json`).
- **`Aouda.Client`** — NuGet version for .NET apps and Hub; tracks API parity with the TS client but versions independently.
- **Studio** — Requires a server reachable at runtime; build-time dependency is only `@aouda/client`.

## Pre-1.0 guidance

While `@aouda/client` is `0.x`:

- Pin **exact** versions in production (`"0.0.1"`, not `"^0.0.1"`).
- Prefer **patch** releases for additive API while on the `0.0.x` line (`0.0.3` → `0.0.4`). A Changesets **minor** bump advances the middle digit (`0.0.3` → `0.1.0`).
- Regenerate TypeScript schema types after server schema changes: `npx @aouda/client generate`.
- **Nothing older is kept compatible** (**0.4.0**). Pre-1.0 the server keeps no compatibility path for older files,
  databases or clients: upgrade the server, its replicas and the SDKs together, and restore older data from a backup taken by
  the new build (or re-create it). In particular: the replication stream speaks **protocol v4 only** — a primary closes a
  v1 / v2 / v3 handshake unanswered, so every node runs the same build; an application database accepts only access tokens
  carrying its URL issuer (`{base}/api/databases/{db}`) — a token issued as `"aouda"` is `401`, while `"aouda"` remains
  the issuer of the server auth database's own tokens; `GET /api/tables` drops `rowCountIsExact`;
  `Aouda.Client` treats a `415` on an insert frame as an error rather than re-sending JSON; and `Decimal(p,s)` is the only
  decimal type (LoadSpeed S13) — a data directory with an undeclared `Decimal` column is refused at open, a `Decimal`
  column or C# `decimal` property that does not declare its precision and scale is refused, and the column-batch frame's 128-bit
  `Decimal` kind (6) is refused, so an older `Aouda.Client` or `@aouda/client` that sends it gets a `400` on that insert
  (see [`Decimal(p,s)`](../guides/schema.md#decimalps-a-decimal-stored-as-a-scaled-integer-columnarcore-s13-020)).
